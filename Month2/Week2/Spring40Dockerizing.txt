PART 1 — Why Containerize?
The problem: "works on my machine"
The root cause: your application and the environment it needs are separate — the app is your code, the environment is whatever happens to be installed on the machine. Containers fix this by bundling them together.

A container is a lightweight, isolated package that bundles your application plus everything it needs to run — the right Java runtime, the dependencies, the config — into one unit that runs the same way on any machine that has Docker.

An image is the blueprint — a read-only template that contains your app + its runtime + dependencies, frozen at build time. You build an image once. It just sits there, like a saved template.

A container is a running instance of an image. You run an image to get a container. The container is the live, executing thing.

Why this fits microservices perfectly
Each service in its own container gives you three things:
Isolation — book-service's dependencies can't clash with borrow-service's. Each carries its own.
Independent deployment — you can rebuild and redeploy just book-service without touching the others.
Independent scaling — run three book-service containers and one of everything else, if book traffic is heavy.

docker images        # lists images (blueprints) you have — you'll see 'redis'
docker ps            # lists running containers (live instances) — you'll see your redis container
docker ps -a         # lists all containers, including stopped ones

Containers solve the 'works on my machine' problem by bundling an application with its runtime and dependencies, so it runs identically across machines. The key distinction is image versus container: an image is a read-only blueprint you build once, and a container is a running instance of it — one image can run many containers, which is how you scale horizontally. Containers are lighter than VMs because they share the host OS kernel instead of bundling a full OS. For microservices, each service runs in its own container for isolation and independent deployment and scaling, and an orchestrator like Docker Compose brings the whole stack up together.

PART 2 — Writing a Dockerfile (turning a service into an image)

A Dockerfile is just a list of commands, each one a build step:

FROM — the starting point: a base image to build on top of (you never start from nothing — you start from, say, a ready-made Java runtime image).
WORKDIR — sets the working directory inside the image (like cd).
COPY — copies files from your machine into the image.
RUN — executes a command at build time (e.g., compile something).
EXPOSE — documents which port the app listens on.
ENTRYPOINT / CMD — the command that runs when a container starts from this image.

docker build -t book-service:1.0.0 ./book-service

It will look for the docker file not in the current location but in current location there is folder called book-service go into that folder and look for file called docker file and build the image with that docker file


A Dockerfile is the build recipe for an image. For a Spring Boot service I start FROM a slim Java 17 runtime, copy the jar in, and set the ENTRYPOINT to java -jar. Each instruction is a cached layer, so I order stable things before volatile ones — in a multi-stage build I resolve dependencies before copying source, so a code change reuses the cached dependency layer and rebuilds fast. Multi-stage also keeps the final image small by shipping only the JRE and jar, without Maven or source. Spring Boot's layered jars take it further by splitting the jar into cacheable layers.

PART 3 — Docker Compose (the whole stack in one file)

In Part 2 you could build and run one service with docker run. But your system has about nine moving parts: MySQL, Redis, Kafka, Eureka, four application services, and the gateway. Running nine separate docker run commands, in the right order, with the right flags, would be worse than your IntelliJ routine. Docker Compose solves this: you describe the entire stack in one YAML file and start it all with a single command.

A file called docker-compose.yml lists each container as a service. Compose starts them all together on one shared network. Your stack has two kinds of services:

Infrastructure — you don't build these, you use ready-made public images: mysql, redis, kafka.
Your apps — you build these from the Dockerfiles you wrote in Part 2: eureka-server, the four services, api-gateway.

Plain depends_on (without a condition) only waits for a container to start — not to be ready. And those are very different:

The MySQL container "starts" in about a second. But MySQL itself needs ~15–20 seconds after that before it actually accepts connections (initializing data dirs, etc.).
So with plain depends_on, book-service starts the moment MySQL's container starts, immediately tries to connect, MySQL isn't accepting connections yet → Connection refused → book-service crashes on boot.

"Started" ≠ "ready." That gap is exactly what bites people, and it's why your dependents need to wait for readiness, not just startup.

The fix: health checks
A health check is a command Docker runs inside a container on a schedule to decide whether it's truly ready. A container moves through states: starting → healthy (or unhealthy). Your MySQL block does this:

healthcheck:
  test: ["CMD", "mysqladmin", "ping", "-h", "localhost", "-uroot", "-proot"]   # 1
  interval: 5s       # 2
  timeout: 3s        # 3
  retries: 15        # 4
  start_period: 20s  # 5

test — the command that decides health. Exit code 0 = healthy, non-zero = not yet. mysqladmin ping succeeds only once MySQL actually answers — so it tests real readiness, not just "process running." (Your Kafka uses kafka-topics --list, Eureka uses wget on /actuator/health — each picks a command that proves that service is genuinely up.)
interval — run the check every 5s.
timeout — if the command takes longer than 3s, count it as a failure.
retries — how many consecutive failures before the container is marked unhealthy.
start_period — a grace window at startup where failures don't count yet — this is what gives a slow service like MySQL time to boot without being prematurely flagged. Important detail people miss.

depends_on with condition — the actual ordering fix
The health check alone just labels the container. The ordering comes from the dependent waiting on that label:

depends_on:
  mysql:
    condition: service_healthy     # wait until MySQL passes its health check

Even with health checks, a robust service should tolerate a dependency blipping after startup (a momentary DB or Kafka hiccup) via connection retries / your Resilience4j patterns. Health checks reduce the startup race; resilience handles the running-state failures. Both layers matter.
Analogy
depends_on: service_started is walking into a restaurant the instant the lights turn on — door's unlocked, but the kitchen's cold and you get turned away. condition: service_healthy is waiting until the restaurant is actually serving — kitchen hot, staff in place. The start_period is the "we open at 12, don't judge us at 11:58" grace window.
Plain words → technical words

container running but not usable yet → "started" vs "ready"
command proving real readiness → health check (test)
grace window at boot → start_period
wait for readiness, not just start → depends_on: condition: service_healthy
"is it alive?" / "can it take traffic?" → liveness / readiness probes
Spring's health endpoint → Actuator /actuator/health


depends_on alone only waits for a container to start, but started isn't ready — MySQL's container is up long before it accepts connections, so a service that boots immediately crashes on connection refused. I add health checks — a command like mysqladmin ping that proves real readiness, with an interval, retries, and a start-period grace window — and have dependents wait with condition: service_healthy. Health checks also matter at runtime: orchestrators restart unhealthy containers and gate traffic on readiness, which in Kubernetes splits into liveness and readiness probes. I back those with Spring Boot Actuator's health endpoint, so health reflects whether critical dependencies are actually up.

Q: Image vs container?
An image is a read-only blueprint built once; a container is a running instance of it. One image can run many containers — that's how you scale horizontally.

Q: Container vs VM?
A VM bundles a whole OS and is heavy and slow to start. A container shares the host kernel and bundles only the app and its dependencies — megabytes, starts in seconds. So you can pack many containers on one host.

Q: What's a Dockerfile?
The build recipe for an image. FROM a base (a Java 17 runtime), COPY the jar in, set ENTRYPOINT to java -jar. Each instruction is a cached layer

Q: Why multi-stage builds / layer caching?
Each instruction is a layer Docker caches, so I order stable things before volatile ones — resolve dependencies before copying source, so a code change reuses the cached dependency layer and rebuilds fast. Multi-stage also keeps the final image small by shipping only the JRE and jar, not Maven or source.

Q: What is Docker Compose?
One YAML file describing the whole multi-container stack — services with their image/build, ports, environment, dependencies, volumes — started together with docker-compose up. It replaces a fragile manual startup.

Q: Why do services use mysql, not localhost?
Inside a container, localhost means that container itself. Compose puts every service on a shared network with internal DNS, so containers reach each other by service name, which resolves to the right container. Published ports are only for host-to-container access.

DNS in general is just a phonebook: you give it a name, it gives you back an address. "google.com" → some IP. On the public internet, big DNS servers do this.
When Docker Compose starts your project, it creates a private virtual network just for your services, and it runs a tiny DNS server inside that network (it lives at the address 127.0.0.11 inside each container network). That DNS server's phonebook is automatically filled with one entry per service.
So "internal DNS" just means: Docker's own private phonebook that maps your service names to the current IP address of each container. You never have to know or manage those IP addresses — you just use the names.

Q: depends_on — isn't that enough for ordering?
No — plain depends_on only waits for a container to start, not to be ready. MySQL's container is up long before it accepts connections. So I add health checks and condition: service_healthy, with a start-period grace window, so dependents wait for real readiness.

Q: Liveness vs readiness?
Liveness asks "is it alive or stuck and needs a restart"; readiness asks "can it take traffic right now." Kubernetes uses both; I back them with Spring Boot Actuator's health endpoint.

The whole system is containerized. Each Spring Boot service has a Dockerfile that packages its jar on a slim Java 17 runtime. A single docker-compose.yml defines the full stack — MySQL, Redis, Kafka, Eureka, the four services, and the gateway — on one shared network. Services address each other by service name, not localhost, and pull their config from a docker Spring profile plus environment overrides. Startup is ordered with health checks and condition: service_healthy, so nothing boots before its dependencies are actually ready. The result is that the entire system comes up with one docker-compose up instead of a manual multi-step routine.
