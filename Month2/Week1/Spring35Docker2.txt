A single-stage Dockerfile uses just one FROM instruction — the entire process (installing dependencies, building, and running) happens inside a single base image, and that one image is your final result. Simple to write; the tradeoff is that the final image carries all the build tools and is larger than it needs to be.

FROM maven:3.9-eclipse-temurin-21
WORKDIR /app
COPY pom.xml .
COPY src ./src
RUN mvn clean package -DskipTests
EXPOSE 8080
CMD ["java", "-jar", "target/library-management-system-0.0.1-SNAPSHOT.jar"]

This single image has Maven and the JDK, builds the jar, and runs it. The downside: Maven and the full JDK ship to production even though you only need a JRE to run the app.
Java (packages a pre-built jar) — if you build with Maven outside Docker first: You only need JRE to run the jar

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY target/library-management-system-0.0.1-SNAPSHOT.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]

RUN -->  executes a command at build time (installing deps, compiling).
EXPOSE — documents which port the app listens on.
CMD / ENTRYPOINT — the command that runs when the container starts. (CMD is easily overridden; ENTRYPOINT is more fixed — they're often used together.)

A multi-stage Dockerfile uses more than one FROM. Each FROM starts a new "stage." You do the heavy building in an early stage (with all the build tools), then start a fresh, clean stage for the final image and copy in only the finished artifact — leaving all the build tooling behind. The result is a much smaller, leaner production image, all from a single Dockerfile.


# ---- Stage 1: build ----
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /app
COPY pom.xml .
COPY src ./src
RUN mvn clean package -DskipTests

# ---- Stage 2: runtime ----
FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /app/target/library-management-system-0.0.1-SNAPSHOT.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]

Stage 1 is discarded — none of its tools or source ship to production.
Stage 2 will be there in the image

When you run docker build, Docker executes both stages, but only the last stage becomes your image. Everything in build is thrown away once its artifact has been extracted.

Why teams almost always prefer this for production:
--> Much smaller images. A single-stage Spring Boot image (Maven + JDK + source + build cache) can run 700 MB–1 GB+. The multi-stage equivalent (JRE + jar) is often around 200–300 MB. Smaller images push, pull, and start faster.
--> Same simplicity. Still one Dockerfile, still one docker build command. You get all the benefit without managing separate build scripts.
--> Smaller attack surface / better security. Compilers, build tools, and your raw source code aren't in the production image, so there's far less for an attacker to exploit, and you're not shipping source.

That's the entire trick. 4× smaller image, no compiler in production, smaller attack surface.

# ============================================================
# STAGE 1 — BUILDER
# ============================================================
FROM maven:3.9-eclipse-temurin-17 AS builder

WORKDIR /build

# Copy parent POM first (multi-module project needs it)
COPY pom.xml /build/pom.xml

# Copy this service's POM
COPY user-service/pom.xml /build/user-service/pom.xml

# Download dependencies (cached layer if POMs don't change)
RUN mvn -f /build/user-service/pom.xml dependency:go-offline -B

# Now copy the actual source code
COPY user-service/src /build/user-service/src

# Build the jar, skip tests (CI runs tests separately)
RUN mvn -f /build/user-service/pom.xml clean package -DskipTests -B

# ============================================================
# STAGE 2 — RUNTIME
# ============================================================
FROM eclipse-temurin:17-jre-alpine

WORKDIR /app

# Copy ONLY the built jar from the builder stage
COPY --from=builder /build/user-service/target/*.jar /app/app.jar

# Document which port this container listens on
EXPOSE 8081

# Run as a non-root user (security best practice)
RUN addgroup -S spring && adduser -S spring -G spring
USER spring:spring

# How to start the app when the container runs
ENTRYPOINT ["java", "-jar", "/app/app.jar"]

Docker Compose is a YAML file that describes a multi-container application, plus a CLI (docker compose up/down/logs) that talks to the Docker daemon to apply that description.

Compose is docker run for many containers, with a shared network and shared lifecycle, declared in one file. Everything you can do in Compose, you could do with a long shell script of docker run commands. Compose just makes it declarative, idempotent, and version-controllable.

You created a network manually and ran two containers on it. Compose automatically creates a default bridge network for all services in the file. Every service gets a DNS name equal to its service name.
So if you define a service called mysql in compose, every other service can reach it at hostname mysql on whatever port it exposes — no IP addresses, no localhost. This is how borrow-service will reach user-service: not via http://localhost:8081 (that's IntelliJ-only), but via http://user-service:8081.

A container's filesystem is temporary. When you remove a container, everything written inside it dies. For your MySQL container, that means: every book, user, borrow record — gone.
A named volume is a piece of host disk that Docker manages, mounted into a container at a specific path. When the container dies, the volume stays. When you create a new container and mount the same volume, your data comes back.

That one line, mysql_data:/var/lib/mysql, reads as two halves separated by the colon:
mysql_data (left) = the name of the locker — a storage box Docker keeps on your host disk, outside any container.
/var/lib/mysql (right) = the folder inside the container where MySQL writes its data.

volumes:
  mysql-data:        # declare a named volume

services:
  mysql:
    volumes:
      - mysql-data:/var/lib/mysql   # mount it where MySQL writes data


Healthchecks — the thing most tutorials get wrong
	borrow-service:
  		depends_on:
    		- mysql
    		- kafka

depends_on without conditions only guarantees that the MySQL container has started — not that MySQL is ready to accept connections. MySQL takes 15-30 seconds to initialize. Your borrow-service Spring Boot app will try to connect, get refused, and crash.

The correct pattern uses healthchecks + condition: service_healthy:

mysql:
  healthcheck:
    test: ["CMD", "mysqladmin", "ping", "-h", "localhost", "-uroot", "-proot"]
    interval: 5s
    timeout: 3s
    retries: 10

borrow-service:
  depends_on:
    mysql:
      condition: service_healthy
Now Compose actually waits until MySQL responds to mysqladmin ping before starting borrow-service.

One for inter-container traffic (other compose services reach Kafka at kafka:9092)
One for host traffic (your IntelliJ or Postman scripts reach Kafka at localhost:29092

Q: Why use Docker Compose instead of just running containers with docker run?
"Compose lets me declare a multi-container application in one YAML file — networks, volumes, dependencies, environment, healthchecks — and bring it all up or tear it all down with one command. Raw docker run works fine for a single container, but the moment I have multiple services that need to talk to each other, like my four Spring Boot services plus MySQL and Kafka, I need things like service-name DNS, ordered startup with healthchecks, named volumes per project, and a single source of truth for the topology. Compose gives all of that for free. The bigger win is that it's declarative: the YAML describes the desired state and Compose reconciles to it. That's the same mental model I'd use with Kubernetes in production, so Compose is a stepping stone, not just a convenience."

Q1: What's the difference between an image and a container?

"An image is an immutable, layered filesystem snapshot — a blueprint. A container is a running instance of that image, with its own writable layer on top. One image can have many containers running off it. Containers are temporary; when you remove one, anything written to its writable layer is gone. Persistent data lives in volumes mounted into the container."

Q2: What's the difference between a virtual machine and a container?
"VMs virtualize the whole hardware stack — each VM runs its own OS kernel on top of a hypervisor. Containers virtualize at the OS level — they share the host's Linux kernel and isolate processes using namespaces and cgroups. That makes containers start in milliseconds vs a VM's minutes, and consume tens of MB vs gigabytes. The tradeoff is isolation: containers share a kernel so a kernel-level vulnerability is more dangerous than in a VM."

Q3: What's a Docker layer? Why does layering matter?
"Every instruction in a Dockerfile that touches the filesystem — FROM, COPY, RUN — creates a new layer. Layers are stacked union-filesystem style; the final image is the union of all layers. Layers are cached: if the inputs to a layer haven't changed since the last build, Docker reuses the cached layer. That's why I copy POMs and run dependency download before copying source code — the slow dependency step gets cached and only re-runs when POMs change."

Q4: Why a multi-stage Dockerfile?
"Two reasons. First, image size — the builder stage has Maven, the JDK, source code, and the .m2 cache, which is over a gigabyte. Only the final stage ends up in the published image, and that's just JRE + my jar, around 250 MB. Second, security — production images don't contain a compiler or build tools, so the attack surface is smaller."

Q5: What's a bind mount vs a named volume?
"Bind mounts map a specific host path into the container — good for source code or config files I want to edit from the host. Named volumes are Docker-managed storage in a daemon-controlled location — good for stateful data like a database, because they have better performance, cleaner permissions, and are portable across machines. In my Compose file I use a bind mount for the MySQL init SQL scripts and a named volume for MySQL data."

Q6: Why is depends_on not enough? What do you use instead?
"Bare depends_on only waits for the dependency container to start, not for the application inside to be ready. MySQL takes 15-25 seconds after the container starts before it accepts connections, so my Spring service would crash trying to connect. The fix is to define a healthcheck on MySQL and use depends_on: condition: service_healthy on the dependent service. That actually waits for the readiness probe to pass."

Q7: How do containers find each other?
"Compose creates a default bridge network per project. Every service gets a DNS name equal to its service name. So my borrow-service can reach the MySQL container at the hostname mysql and Kafka at kafka — no IP addresses, no localhost. localhost inside a container refers to the container itself, which is a classic gotcha when you containerize an app that previously used localhost URLs."

Q8: How do you configure the same image for dev and prod?
"Configuration comes from environment variables, not the image. The image is built once and is identical across environments. In Spring Boot, environment variables override application.yml values via Spring's relaxed binding, so SPRING_DATASOURCE_URL in Compose overrides spring.datasource.url in YAML. For Feign client URLs that aren't standard Spring properties, I use placeholder syntax like ${user-service.url:http://localhost:8081} — env var wins in Compose, default kicks in locally from IntelliJ. This is the 12-factor app principle: same code and same image, different config per environment."

Q10: Walk me through what happens when you run docker compose up.
"Compose parses the YAML, computes the desired state, and asks the Docker daemon to reconcile. The daemon creates the bridge network if missing, creates declared volumes if missing, pulls any images not present locally, then starts containers respecting depends_on ordering. For each container with a healthcheck, Compose waits for it to be healthy before starting anything that depends on it. Each container gets connected to the project network with its service name as DNS, gets the environment variables injected, has volumes mounted, and runs its ENTRYPOINT. Once all containers are up, Compose either streams logs (foreground) or returns (with -d)."

Q11: How do containers communicate over the network — what's actually happening under the hood?
"Each container gets a virtual network interface attached to the bridge network — basically a software switch managed by the Docker daemon. The daemon also runs an embedded DNS server on 127.0.0.11 inside every container, which resolves service names to the container IPs on that network. So when Spring's Feign client does an HTTP call to http://user-service:8081, the JVM asks the OS to resolve user-service, the OS asks 127.0.0.11, gets the IP, and opens a TCP connection over the bridge. To the application, it looks identical to calling any external HTTP service."
