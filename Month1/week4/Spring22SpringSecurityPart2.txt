In Spring Security, a role is just an authority with a ROLE_ prefix. That's it at the code level. They're the same underlying concept — GrantedAuthority objects attached to a user.

Authority is the generic, lower-level concept. It represents any permission or privilege a user has. It's just a string. Examples:
READ_PRIVILEGES
WRITE_PRIVILEGES
DELETE_USER
ROLE_ADMIN

Role is a higher-level grouping — typically a bundle of authorities that represents a job or persona. By Spring convention, roles are stored as authorities prefixed with ROLE_

Q1: "What happens when you add spring-boot-starter-security to a Spring Boot app?"

"Spring Boot's SecurityAutoConfiguration registers a default SecurityFilterChain that locks every endpoint behind authentication. It generates a random password for a user named 'user' and prints it to the console. Browsers get redirected to a default login page; REST clients get 401 with a Basic auth challenge. CSRF is enabled, HTTP sessions are created. For REST APIs, you immediately override these defaults with your own SecurityFilterChain bean — disabling CSRF, switching to stateless sessions, and configuring real auth rules."

Q2: "Why does the random password change every restart?"

"Because it's auto-generated by SecurityProperties at startup as a development convenience. It's intentionally not persisted — Spring's design forces you to provide a real UserDetailsService with persisted users before going to production. The console message even says 'for development use only'."

Q3: "What does 'secure by default' mean and why does Spring Security do it?"

"It means the framework defaults to denying every request unless you explicitly allow it. The reasoning: forgetting to lock an endpoint is a worse failure than forgetting to unlock one. If defaults were 'allow', a developer who forgot to write rules would silently leak data. With 'deny', they immediately see 401 in testing and fix it. It's a fail-safe design."

Q4: "Why disable CSRF for REST APIs?"

"CSRF protection assumes browser-cookie-based sessions, where a malicious site can trick a user's browser into sending requests with their cookies. With JWT in Authorization headers, there's no automatic cookie attachment by the browser to other domains, so CSRF doesn't apply. Disabling it removes a useless layer of friction for token-based auth."

Q5: "What's the difference between SessionCreationPolicy.STATELESS and ALWAYS?"

"STATELESS tells Spring NOT to create or use HTTP sessions — every request must carry its own auth (perfect for JWT). ALWAYS forces session creation even when not needed. For REST APIs we use STATELESS so the server holds no per-user state, making horizontal scaling trivial."

Q1: "What does @EnableWebSecurity do?"

"It activates Spring Security's web integration — wiring my custom SecurityFilterChain into the servlet filter chain. In modern Spring Boot, auto-configuration often does this implicitly, but adding it explicitly is good practice."

Q2: "Walk me through every line of a basic SecurityFilterChain config."

"csrf().disable() removes CSRF protection because it's irrelevant for stateless APIs using JWT in headers — no automatic cookie attachment means no CSRF risk. sessionManagement().sessionCreationPolicy(STATELESS) tells Spring not to create or use HTTP sessions, since JWT carries auth on every request. authorizeHttpRequests() defines URL-to-permission rules — they're evaluated top-down, first match wins, with anyRequest() always last. .build() constructs the immutable filter chain bean."

Q3: "Why use BCrypt instead of SHA-256 for passwords?"
"SHA-256 is designed to be FAST — that's the opposite of what you want for passwords. A modern GPU can compute billions of SHA-256 hashes per second, making brute-force attacks feasible. BCrypt is intentionally slow with a tunable work factor — about 100ms per hash. To users it's invisible; to attackers it makes brute-force economically infeasible. BCrypt also auto-handles salting and embeds the cost factor in the hash."

Q4: "What's the difference between permitAll() and authenticated()?"
"permitAll() allows anyone — no auth needed. authenticated() requires the user to be logged in (any role works). Use permitAll() for public endpoints like login and signup; authenticated() for any logged-in user; hasRole('ADMIN') for role-specific access."

Q5: "Why is STATELESS important and what would happen without it?"
"Without STATELESS, Spring may create HTTP sessions even for JWT-authenticated requests, leading to: memory bloat (server stores millions of sessions), broken horizontal scaling (sessions tied to specific servers without sticky sessions), and security risks (session fixation attacks). STATELESS forces every request to carry its own auth via JWT — perfect for scalable, microservice-friendly APIs."
