What Problem Does Spring Security Solve?
Imagine Your App WITHOUT Spring Security
Right now, your Library Management System has endpoints like:

@RestController
public class BookController {
    
    @GetMapping("/api/books")
    public List<Book> getAllBooks() {
        return bookRepo.findAll();
    }
    
    @PostMapping("/api/books")
    public Book createBook(@RequestBody Book book) {
        return bookRepo.save(book);
    }
    
    @DeleteMapping("/api/books/{id}")
    public void deleteBook(@PathVariable Long id) {
        bookRepo.deleteById(id);
    }
}

Anyone in the world can hit these URLs

The 3 Core Questions Every Web App Must Answer
Before letting any request reach your controller, you must answer:
1) "Who is making this request?" → Authentication (AuthN)
2) "Are they allowed to do this action?" → Authorization (AuthZ)
3) "How do I track who they are across requests?" → Session management (or JWT)

Spring Security handles ALL THREE for you. That's its job

Without Spring Security

Browser → Tomcat → DispatcherServlet → @Controller → DB
                                       ↑
                              Direct access. No checks.

With Spring Security

Browser → Tomcat → [SECURITY FILTER CHAIN] → DispatcherServlet → @Controller → DB
                       ↑
            15+ filters check identity,
            permissions, CSRF, session,
            etc., BEFORE reaching your code

Every request must pass through the filter chain before your business logic ever runs. If any filter rejects it → 401/403 returned, controller never invoked

Two Big Words You'll Hear Constantly
Authentication (AuthN) = "Who are you?"
	Verifying identity (username + password, JWT token, OAuth)
	Result: a Principal object representing the user
Authorization (AuthZ) = "What can you do?"
	Checking permissions (Are you ADMIN? Can you edit this book?)
	Result: allow ✅ or deny ❌

What Spring Security Gives You for Free
When you add the dependency spring-boot-starter-security, you get:

✅ Default login page (out of the box)
✅ HTTP Basic Authentication support
✅ CSRF protection (cross-site request forgery)
✅ Session management
✅ Password hashing utilities (BCrypt)
✅ Role-based access control (@PreAuthorize, etc.)
✅ Integration points for OAuth, JWT, LDAP, SAML, etc.
✅ The whole filter chain architecture

Spring Security is a framework that intercepts every HTTP request before it reaches your controller, performs authentication and authorization checks via a chain of filters, and stores the result in a thread-local SecurityContext. It handles everything from basic login forms to OAuth2 to JWT-based stateless APIs — all configured declaratively through a SecurityFilterChain bean.

The Spring Security Filter Chain

What Is a "Filter"?
A filter in Java web development = a piece of code that runs BEFORE or AFTER every HTTP request, sitting between the network and your servlet (controller).

Request                                Response
Browser ──────→ [Filter 1] [Filter 2] ... ──→ Servlet ──→ ... [Filter 2] [Filter 1] ──→ Browser
                                                ↑
                                        (Your @Controller)

Filters can:
	Inspect / modify the request (read headers, check auth)
	Block the request (return 401, 403)
	Log details (URL, IP, timing)
	Pass it on to the next filter

Spring Security IS a Chain of Filters
When you add spring-boot-starter-security, Spring registers a single Servlet filter with Tomcat:
FilterChainProxy   ← Spring Security's master filter

Request → FilterChainProxy
              ↓
         ┌──────────────────────────────────┐
         │  1. SecurityContextPersistenceFilter
         │  2. WebAsyncManagerIntegrationFilter
         │  3. HeaderWriterFilter
         │  4. CsrfFilter
         │  5. LogoutFilter
         │  6. UsernamePasswordAuthenticationFilter
         │  7. ConcurrentSessionFilter
         │  8. BearerTokenAuthenticationFilter   ← JWT lives here (later!)
         │  9. RequestCacheAwareFilter
         │ 10. SecurityContextHolderAwareRequestFilter
         │ 11. AnonymousAuthenticationFilter
         │ 12. SessionManagementFilter
         │ 13. ExceptionTranslationFilter
         │ 14. AuthorizationFilter
         └──────────────────────────────────┘
              ↓
         Your @Controller (only if all filters approved!)

Each filter has one specific responsibility. They run in order. Any one can stop the request from going further.

1. SecurityContextPersistenceFilter (or SecurityContextHolderFilter in newer versions)
	Loads existing authentication from session/cookies into the SecurityContextHolder (thread-local). Saves it back at the end.
This is how Spring "remembers" you're logged in across multiple requests

2. CsrfFilter
	Protects against Cross-Site Request Forgery attacks. Requires a CSRF token on POST/PUT/DELETE requests.
We disable this for stateless REST APIs (you'll see this in your config: csrf.disable()). Why? Because CSRF protects against browser-cookie-based sessions; with JWT in headers, it's not applicable
We disable this for stateless REST APIs (you'll see this in your config: csrf.disable()). Why? Because CSRF protects against browser-cookie-based sessions; with JWT in headers, it's not applicable.

3. UsernamePasswordAuthenticationFilter
Handles /login form submissions. Reads username and password, calls the AuthenticationManager, creates an Authentication object on success.
If you're using a login form → this is your guy. For JWT, we replace this with our own filter

4.  BearerTokenAuthenticationFilter (or your custom JwtAuthenticationFilter)
Reads Authorization: Bearer <token> header, validates JWT, and creates an Authentication object.
This is the filter you'll write yourself this week. 

5. AuthorizationFilter (formerly FilterSecurityInterceptor)
The LAST filter. Checks if the authenticated user has permission to access the requested URL. Throws AccessDeniedException if not.
This is what enforces rules like "only ADMIN can DELETE /api/books".

Let's trace what happens when a user tries to delete a book with a JWT: 

DELETE /api/books/42
Headers: Authorization: Bearer eyJhbGc...

Step 1: Tomcat receives request
        ↓
Step 2: FilterChainProxy intercepts (Spring Security's master filter)
        ↓
Step 3: SecurityContextPersistenceFilter
        → No session → SecurityContext is empty for now
        ↓
Step 4: HeaderWriterFilter
        → Adds security headers to RESPONSE (X-Frame-Options, etc.)
        ↓
Step 5: CsrfFilter
        → Disabled (stateless API)
        ↓
Step 6: JwtAuthenticationFilter (your custom filter)
        → Extract JWT from "Authorization: Bearer ..."
        → Validate signature + expiry
        → Load user from DB (UserDetailsService)
        → Build Authentication object: { principal: "alice@lib.com", authorities: [ROLE_ADMIN] }
        → Store in SecurityContextHolder
        ↓
Step 7: AnonymousAuthenticationFilter
        → User already authenticated → skip
        ↓
Step 8: AuthorizationFilter
        → URL is /api/books/42, method is DELETE
        → Config says: "DELETE /api/books/** requires ROLE_ADMIN"
        → User has ROLE_ADMIN → ✅ allow
        ↓
Step 9: DispatcherServlet
        ↓
Step 10: @DeleteMapping("/api/books/{id}") in BookController
        ↓
Step 11: Book deleted, 204 returned
        ↓
Step 12: Response flows back through filters in REVERSE order
        ↓
Browser receives response

What happens when a filter rejects

Step 6: JwtAuthenticationFilter
        → JWT is expired ❌
        → Don't store anything in SecurityContextHolder
        → Pass to next filter (still allowed)

Step 8: AuthorizationFilter
        → No authentication present
        → URL requires authentication
        → Throw AccessDeniedException
        ↓
Step 13: ExceptionTranslationFilter (catches it!)
        → Translates to HTTP 401 Unauthorized
        ↓
Browser receives: HTTP 401

Q: "Where exactly does Spring Security run in the request lifecycle?"
"Spring Security registers a single servlet filter — FilterChainProxy — that contains an internal chain of 15+ specialized filters. Each handles one concern: CSRF, authentication, authorization, etc. The chain runs BEFORE the DispatcherServlet, so any failed check returns 401/403 without ever invoking your @Controller. After the controller runs, response flows back through the same filters in reverse order."


When configuring Spring Security, you typically:

Disable filters you don't need (CSRF for stateless APIs)
Add custom filters (your JwtAuthenticationFilter)
Configure existing filters (which URLs require auth, which roles)

You almost never write entire filters from scratch (except your JWT one) — you just plug into the existing chain.

http
    .csrf(csrf -> csrf.disable())                              // Remove CsrfFilter behavior
    .authorizeHttpRequests(auth -> auth
        .requestMatchers("/api/admin/**").hasRole("ADMIN")     // Configure AuthorizationFilter
        .anyRequest().authenticated()
    )
    .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class);  // Insert custom JWT filter

A filter runs before/after every HTTP request, can inspect/block it
Spring Security adds ONE servlet filter (FilterChainProxy) that internally contains 15+ specialized filters
The chain runs BEFORE your @Controller — failed checks return 401/403 directly
Each filter has one job (CSRF, auth, authz, etc.) — Single Responsibility Principle
You configure the chain (disable CSRF, add JWT, set rules) — you don't rewrite it

SecurityContextHolder       ← The OUTER container (thread-local storage)
    ↓ contains
SecurityContext             ← Holds ONE Authentication object
    ↓ contains
Authentication              ← Represents the logged-in user
    ↓ contains

    └── Authorities         ← WHAT they can do (roles/permissions)

1️⃣ SecurityContextHolder — The Storage Locker
Imagine your app handles 100 requests at the same time. Each request belongs to a different user:

Request 1: Alice (ROLE_ADMIN)
Request 2: Bob (ROLE_USER)
Request 3: Charlie (ROLE_USER)

When Alice's controller runs, how does Spring know it's Alice and not Bob? They're processed by different threads, sometimes on the same server.
Solution: Store the user info in a thread-local variable — a special kind of variable that has a different value for each thread. 

SecurityContextHolder = a static class that stores the current request's authentication info in thread-local storage.

// Anywhere in your code, on any thread:
Authentication auth = SecurityContextHolder.getContext().getAuthentication();

This works everywhere — services, controllers, repositories, utility methods. As long as the request is in flight, you can access who's making it.

🧵 What Is "Thread-Local"?
A normal variable is shared across the program. A thread-local variable has a separate value per thread:

Thread #1 (handling Alice's request)
    SecurityContextHolder.context = { auth: Alice }

Thread #2 (handling Bob's request)
    SecurityContextHolder.context = { auth: Bob }

Same global accessor, different stored values! 🪄

When Alice's controller calls SecurityContextHolder.getContext() → it gets Alice's data.
When Bob's controller calls the same method → it gets Bob's data.
Each thread has its own "locker" in the SecurityContextHolder.

@RestController
@RequestMapping("/api/users")
public class UserController {
    
    @GetMapping("/me")
    public ResponseEntity<UserResponse> getCurrentUser() {
        // Pull the current user from thread-local storage
        Authentication auth = SecurityContextHolder.getContext().getAuthentication();
        String email = auth.getName();   // "alice@lib.com"
        return ResponseEntity.ok(userService.findByEmail(email));
    }
}

This /me endpoint returns whatever user is making the request. No need to pass user ID as a parameter — Spring Security already knows.


@GetMapping("/me")
public void getCurrentUser() {
    Authentication auth = SecurityContextHolder.getContext().getAuthentication();
    System.out.println(auth.getName());  // ✅ Works — same thread
    
    new Thread(() -> {
        Authentication auth2 = SecurityContextHolder.getContext().getAuthentication();
        System.out.println(auth2);       // ❌ NULL — different thread, no context!
    }).start();
}

2️⃣ Authentication — The "ID Card"
Authentication is an interface representing the currently logged-in user. Think of it as their ID card — it carries everything important about them.
public interface Authentication {
    Object getPrincipal();                          // WHO (the user object)
    Collection<GrantedAuthority> getAuthorities();  // WHAT (their roles/permissions)
    Object getCredentials();                        // PASSWORD (cleared after auth!)
    boolean isAuthenticated();                      // Are they actually logged in?
    String getName();                               // Convenience: usually email/username
}

Authentication auth = SecurityContextHolder.getContext().getAuthentication();

// 1. WHO are they?
UserDetails principal = (UserDetails) auth.getPrincipal();
//                                              ↑
//                                  Usually a UserDetails object (your User entity)

// 2. WHAT can they do?
Collection<? extends GrantedAuthority> roles = auth.getAuthorities();
//   Returns: [ROLE_ADMIN, ROLE_USER, ...]

// 3. Their credentials (if applicable — usually NULL after auth completes)
Object creds = auth.getCredentials();
//   Spring CLEARS the password after successful auth for security 🛡️

// 4. Are they actually authenticated?
boolean isAuth = auth.isAuthenticated();
//   true = logged in, false = anonymous

// 5. Their "name" (usually email or username)
String email = auth.getName();
//   Shortcut for: principal.getUsername()

BearerTokenAuthentication					OAuth2 / JWT-based authentication

3️⃣ Principal — The Actual User

The Principal is the actual user object. It answers: "Whose account is this?"
In Spring Security, this is almost always an instance of UserDetails:

public interface UserDetails {
    String getUsername();                              // Usually email
    String getPassword();                              // Hashed password (BCrypt)
    Collection<? extends GrantedAuthority> getAuthorities();  // Roles
    boolean isEnabled();                                // Account active?
    boolean isAccountNonExpired();                      // Account expired?
    boolean isAccountNonLocked();                       // Account locked?
    boolean isCredentialsNonExpired();                  // Password expired?
}

public class CustomUserDetails implements UserDetails {
    
    private final User user;   // Your JPA entity
    
    public CustomUserDetails(User user) {
        this.user = user;
    }
    
    @Override
    public String getUsername() {
        return user.getEmail();
    }
    
    @Override
    public String getPassword() {
        return user.getPassword();    // Hashed (BCrypt)
    }
    
    @Override
    public Collection<? extends GrantedAuthority> getAuthorities() {
        return List.of(new SimpleGrantedAuthority("ROLE_" + user.getRole()));
    }
    
    @Override public boolean isEnabled() { return true; }
    @Override public boolean isAccountNonExpired() { return true; }
    @Override public boolean isAccountNonLocked() { return true; }
    @Override public boolean isCredentialsNonExpired() { return true; }
    
    public User getUser() { return user; }   // Convenient access to original entity
}


Why a wrapper? Keeps your JPA User entity clean — it shouldn't know about Spring Security details

For simple cases, Spring provides a built-in implementation:

import org.springframework.security.core.userdetails.User;

UserDetails user = User.withUsername("alice@lib.com")
    .password("{bcrypt}$2a$10$...")
    .roles("ADMIN", "USER")
    .build();

Use this for tests or quick prototypes. For production, write your own CustomUserDetails

4️⃣ GrantedAuthority — What They Can Do

A GrantedAuthority is a single permission the user has. It's just a string wrapped in an interface:

public interface GrantedAuthority {
    String getAuthority();   // e.g., "ROLE_ADMIN", "READ_BOOKS", "DELETE_USERS"
}

The "ROLE_" prefix is a Spring convention. When you call hasRole("ADMIN"), Spring automatically adds ROLE_ and checks for ROLE_ADMIN

.requestMatchers("/admin/**").hasRole("ADMIN")    // Looks for "ROLE_ADMIN"
.requestMatchers("/admin/**").hasAuthority("ROLE_ADMIN")  // Same thing — explicit
.requestMatchers("/admin/**").hasAuthority("DELETE_BOOKS") // Permission-based

Roles = broad categories (ADMIN, USER, MANAGER)
Permissions/Authorities = fine-grained actions (DELETE_BOOKS, EDIT_PROFILE)


1. JwtAuthenticationFilter validates her JWT
2. It loads Alice's user from DB:
       User user = userRepo.findByEmail("alice@lib.com")
3. Wraps it as UserDetails:
       UserDetails principal = new CustomUserDetails(user)
4. Builds authorities:
       List<GrantedAuthority> authorities = List.of(
           new SimpleGrantedAuthority("ROLE_ADMIN")
       )
5. Creates Authentication object:
       Authentication auth = new UsernamePasswordAuthenticationToken(
           principal,        // ← WHO
           null,             // ← Credentials (cleared)
           authorities       // ← WHAT
       )
       auth.setAuthenticated(true)
6. Stores in thread-local:
       SecurityContextHolder.getContext().setAuthentication(auth)
7. Request continues to AuthorizationFilter
8. AuthorizationFilter checks: "Does ROLE_ADMIN match the rule?"
       YES → request reaches controller
9. In controller, Alice can access:
       SecurityContextHolder.getContext().getAuthentication().getName()
       → "alice@lib.com"


How to Access the Current User in Your Code

@GetMapping("/me")
public UserResponse getMe(Authentication auth) {
    return userService.findByEmail(auth.getName());
}

@GetMapping("/me")
public UserResponse getMe(@AuthenticationPrincipal CustomUserDetails userDetails) {
    return userService.findByEmail(userDetails.getUsername());
}


Q1: "Where is the currently authenticated user stored, and how do you access it?"
"It's stored in SecurityContextHolder, which uses thread-local storage by default. From any code in the request thread, I call SecurityContextHolder.getContext().getAuthentication(). In controllers, I prefer injecting Authentication as a parameter or using @AuthenticationPrincipal — Spring auto-populates them."

Q2: "Why is SecurityContextHolder thread-local? What if I spawn a new thread?"
"Thread-local ensures each concurrent request has its own context — Alice's data doesn't leak into Bob's request even on the same JVM. But if I spawn a child thread with new Thread(), the context doesn't propagate — it's null in the child. For async code, I'd use @Async with the right configuration, or pass auth info explicitly."

Q3: "Difference between Principal and Authentication?"
"Authentication is the bigger object — it contains the principal, authorities, credentials, and authenticated state. Principal is just one field inside Authentication — usually a UserDetails representing the user object. Think of Authentication as the 'ID card' and Principal as the 'name on the card'."

Q4: "Difference between roles and authorities?"
"Spring uses authority as the umbrella term. A role is just an authority with the 'ROLE_' prefix — a Spring convention. hasRole('ADMIN') looks for ROLE_ADMIN; hasAuthority('ROLE_ADMIN') is explicit. Roles are broad categories like ADMIN/USER; authorities can also represent fine-grained permissions like DELETE_BOOKS."

Q5: "What does auth.isAuthenticated() return for an anonymous user?"
"It returns true because Spring creates an AnonymousAuthenticationToken for unauthenticated requests — it's still 'authenticated' as the anonymous user. To check for real users, call auth instanceof AnonymousAuthenticationToken or check authorities for ROLE_ANONYMOUS."

Stateless REST API The server doesn't remember anything about previous requests. Every request must contain all the information needed to process it.

GET /api/orders/123
Authorization: Bearer eyJhbGc...   ← every request includes who you are

Stateful REST API The server remembers context between requests — usually via a session ID stored on the server.

POST /api/login           → server creates session, returns SESSION_ID=abc123
GET /api/orders/123       
Cookie: SESSION_ID=abc123  ← server looks up "who is abc123?" in memory

	Let's say you're logged into your bank: mybank.com. Your browser holds a session cookie.To transfer money, the bank uses:
	POST https://mybank.com/transfer
	Cookie: SESSION_ID=abc123
	Body: amount=1000&to=friend

	Now, while still logged in, you visit a completely different site: evilcat.com (looks like a cat photo blog).
	The attacker has hidden this in the page:
	<form action="https://mybank.com/transfer" method="POST" id="evil">
   		 <input name="amount" value="50000">
    		<input name="to" value="attacker_account">
	</form>
	<script>document.getElementById('evil').submit();</script>
	
	When you load evilcat.com:

	The hidden form auto-submits to mybank.com/transfer
	Your browser automatically includes your bank session cookie (because that's how cookies work)
	The bank sees a valid session cookie and processes the transfer
	$50,000 gone, you saw nothing but a cat photo

	Why it works
	Browsers send cookies for a domain automatically with every request to that domain — regardless of which site triggered the request. The bank 	server can't tell whether the request came from:

	You clicking "Transfer" on mybank.com ✅ legitimate
	A hidden form on evilcat.com ❌ malicious

	Real-world CSRF attack vectors
	CSRF doesn't need a <form> tag. Even a simple image tag can do it:

	<img src="https://mybank.com/transfer?amount=1000&to=hacker" />

What makes a site vulnerable
A site is vulnerable to CSRF if:

✅ Uses cookies for authentication (most web apps)
✅ Allows state-changing requests (POST, PUT, DELETE)
❌ Doesn't have CSRF protection

How to prevent CSRF
1. CSRF tokens (most common defense)
The server generates a random, unique token tied to the user's session and includes it in every form:

<form action="/transfer" method="POST">
    <input type="hidden" name="csrf_token" value="x7G9pQ3mZ8...">
    <input name="amount">
    <input name="to">
    <button>Transfer</button>
</form>

When the form submits, the server checks: "Did this request include the CSRF token I issued? Does it match the user's session?"
evilcat.com can't read your token (Same-Origin Policy), so it can't include the right value → request rejected.
