Spring Bean Lifecycle — The Full Order
1. Spring scans and registers BeanDefinitions (just metadata, NO objects yet)
2. BeanFactoryPostProcessors run (e.g. PropertySourcesPlaceholderConfigurer)
3. Singleton beans get instantiated (constructor called)
4. Dependencies get injected (@Autowired fields/setters)
5. @PostConstruct runs
6. Bean is ready to use

@Component
public class EngineService {

    public EngineService() {
        System.out.println("1. EngineService CONSTRUCTOR called — object created");
    }

    @PostConstruct
    public void init() {
        System.out.println("4. EngineService @PostConstruct");
    }
}

@Component
public class WheelService {

    public WheelService() {
        System.out.println("1. WheelService CONSTRUCTOR called — object created");
    }

    @PostConstruct
    public void init() {
        System.out.println("4. WheelService @PostConstruct");
    }
}


@Component
public class CarService {

    @Autowired
    private EngineService engineService;   // will be injected BEFORE @PostConstruct

    @Autowired
    private WheelService wheelService;     // will be injected BEFORE @PostConstruct

    public CarService() {
        // At this exact moment:
        // - CarService object EXISTS in memory
        // - engineService is NULL  ← NOT injected yet
        // - wheelService is NULL   ← NOT injected yet
        System.out.println("2. CarService CONSTRUCTOR called");
        System.out.println("   engineService inside constructor = " + engineService); // prints null
        System.out.println("   wheelService inside constructor = " + wheelService);   // prints null
    }

    @PostConstruct
    public void init() {
        // At this exact moment:
        // - engineService is INJECTED ✅
        // - wheelService is INJECTED ✅
        System.out.println("3. CarService @PostConstruct");
        System.out.println("   engineService = " + engineService); // prints real object
        System.out.println("   wheelService = " + wheelService);   // prints real object
    }
}


It always first creates the object then whatever the object created if that class has post construct before that dependent beans if any gets injected and the @PostConstruct runs

1. EngineService CONSTRUCTOR called — object created
4. EngineService @PostConstruct
1. WheelService CONSTRUCTOR called — object created
4. WheelService @PostConstruct
2. CarService CONSTRUCTOR called
   engineService inside constructor = null
   wheelService inside constructor = null
3. CarService @PostConstruct
   engineService = com.example.EngineService@1a2b3c
   wheelService = com.example.WheelService@4d5e6f


What if you use Constructor Injection?
This is the KEY difference — with constructor injection, dependencies ARE available inside the constructor itself.

@Component
public class CarService {

    private final EngineService engineService;
    private final WheelService wheelService;

    @Autowired
    public CarService(EngineService engineService, WheelService wheelService) {
        // Spring MUST create EngineService and WheelService FIRST
        // before it can even call this constructor
        // So both are available here ✅
        this.engineService = engineService;
        this.wheelService = wheelService;
        System.out.println("CarService CONSTRUCTOR called");
        System.out.println("engineService = " + engineService); // NOT null ✅
        System.out.println("wheelService = " + wheelService);   // NOT null ✅
    }

    @PostConstruct
    public void init() {
        // Also available here ✅
        System.out.println("CarService @PostConstruct");
        System.out.println("engineService = " + engineService); // NOT null ✅
    }
}




Filter vs Interceptor + OncePerRequestFilter + RequestLoggingFilter

// You have 10 controllers, 50 endpoints
// Every request needs:
// → Logging (method, URL, response time)
// → Auth check (is token valid?)
// → CORS headers

// WITHOUT Filter/Interceptor:
@GetMapping("/books")
public ResponseEntity getBooks() {
    log.info("GET /books started");  // repeated in every method
    // check auth...                 // repeated in every method
    // your actual logic
    log.info("GET /books took 5ms"); // repeated in every method
}

// 50 endpoints = 50 copies of same code ❌
// WITH Filter/Interceptor → write once, applies everywhere ✅

A Filter is a component that intercepts HTTP requests and responses before they reach the Servlet (DispatcherServlet in Spring) or after the response leaves it.
It sits at the Servlet container level (Tomcat/Jetty) — completely outside of Spring's world.
Think of it like a security checkpoint at the entrance of a building — everyone must pass through it regardless of where they're going inside.

Why do we need filters

Without filters, you'd have to write the same repetitive logic in every single controller/servlet:

Check if the request has a valid token → in every controller
Log every request → in every controller
Add CORS headers → in every controller
Decompress request body → in every controller

Filters let you write this logic once and apply it globally or to specific URL patterns


Client Request
      |
      ▼
+------------------+
|   Filter Chain   |  ← Servlet Container (Tomcat)
|                  |
|  Filter 1        |  (e.g., Logging Filter)
|      ↓           |
|  Filter 2        |  (e.g., Auth Filter)
|      ↓           |
|  Filter 3        |  (e.g., CORS Filter)
|      ↓           |
+------------------+
      |
      ▼
DispatcherServlet   ← Spring starts here
      |
      ▼
   Controller

The key concept is the FilterChain — each filter decides whether to:

	Pass the request to the next filter via chain.doFilter()
	Block the request entirely (e.g., unauthorized)



Servlet Container starts
        |
        ▼
   init()         ← called once when filter is created
        |
        ▼
   doFilter()     ← called on every matching request
        |
        ▼
   destroy()      ← called once when container shuts down




@Component
public class MyFilter implements Filter {

    @Override
    public void init(FilterConfig filterConfig) throws ServletException {
        // called once at startup — setup resources
        System.out.println("Filter initialized");
    }

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {

        HttpServletRequest httpRequest = (HttpServletRequest) request;

        System.out.println("BEFORE - Request URI: " + httpRequest.getRequestURI());

        chain.doFilter(request, response); // pass to next filter or servlet

        System.out.println("AFTER - Response sent");
    }

    @Override
    public void destroy() {
        // called once at shutdown — release resources
        System.out.println("Filter destroyed");
    }
}


1. Authentication / Authorization Filter
Checks if the request has valid credentials before allowing it through.
2. Logging Filter
Logs every incoming request and outgoing response.
3. CORS Filter
Adds Cross-Origin Resource Sharing headers to every response.
4. Request/Response Modification Filter
Modifies request body or response body (e.g., encryption, compression).
5. Rate Limiting Filter
Limits how many requests a client can make in a time window.


Ways to Register a Filter
Option 1 — @Component (applies to all URLs)
Option 2 — @WebFilter (specific URL patterns)
Option 3 — FilterRegistrationBean (full control)


When you have multiple filters, order matters:

@Bean
public FilterRegistrationBean<LoggingFilter> loggingFilter() {
    FilterRegistrationBean<LoggingFilter> bean = new FilterRegistrationBean<>();
    bean.setFilter(new LoggingFilter());
    bean.setOrder(1); // runs first
    return bean;
}

@Bean
public FilterRegistrationBean<AuthFilter> authFilter() {
    FilterRegistrationBean<AuthFilter> bean = new FilterRegistrationBean<>();
    bean.setFilter(new AuthFilter());
    bean.setOrder(2); // runs second
    return bean;
}



Advantage			Explanation
Reusability			Write once, apply to all matching URLs
Separation of concerns		Keep cross-cutting logic out of business code
Works on everything		Applies to static files, servlets, Spring controllers
Language standard		Part of Jakarta EE, works outside Spring too
Early interception		Can block request before Spring processes it



This is a basic filter , and there is a problem associated with that

One request can be dispatched MULTIPLE times internally.
Example:
→ Request comes in         → Filter runs (1st time)
→ Exception thrown
→ Spring forwards to /error → Filter runs (2nd time) ❌

Same filter runs twice for one user request.
Logging appears twice. Auth checked twice.

OncePerRequestFilter  : The Right Way

// OncePerRequestFilter — Spring's solution
// Guarantees doFilterInternal runs EXACTLY ONCE
// per request — no matter how many dispatches

@Component
public class MyFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(
            HttpServletRequest request,      // ← typed as HttpServletRequest
            HttpServletResponse response,    // ← typed as HttpServletResponse
            FilterChain chain)
            throws ServletException, IOException {

        // Your logic here — runs exactly once ✅

        chain.doFilter(request, response); // pass to next filter/controller
    }
}


Basic Filter         → might run multiple times ❌


OncePerRequestFilter → guaranteed once ✅

Also gives you:
→ HttpServletRequest  (not raw ServletRequest)
→ HttpServletResponse (not raw ServletResponse)
→ Typed — can call .getHeader(), .getStatus() directly
→ No casting needed

How it guarantees once : 

// Internally OncePerRequestFilter does this:
String alreadyFilteredAttr = "MyFilter.FILTERED";
if (request.getAttribute(alreadyFilteredAttr) != null) {
    chain.doFilter(request, response); // skip — already ran
    return;
}
request.setAttribute(alreadyFilteredAttr, true); // mark as ran
doFilterInternal(request, response, chain);       // run your code


In a Spring application, a single client request can trigger multiple dispatches internally , means it passes through same filter multiple times
--> If any exception occurs
--> Internally in a controller method if we forward the method to another api call

so we use once per request filter


INTERCEPTOR
An Interceptor is a component that intercepts HTTP requests but at the Spring MVC level, meaning it sits inside the DispatcherServlet, not before it like a Filter.
It has access to the Spring context, knows which controller and method will handle the request, and gives you 3 specific hook points to plug your logic into
Think of it like a receptionist inside the building — the security checkpoint (Filter) already let you in, now the receptionist decides where you go, checks your appointment, and follows up after your meeting.


Filters are powerful but they are blind to Spring's world :
	They don't know which controller is handling the request
	They can't access Spring beans easily
	They can't access ModelAndView
	They work on raw ServletRequest, not Spring abstractions


Client Request
      |
      ▼
+------------------+
|  Filter Chain    |  ← Servlet Container (Tomcat)
+------------------+
      |
      ▼
DispatcherServlet   ← Spring boundary
      |
      ▼
+----------------------+
|  Interceptor         |
|                      |
|  1. preHandle()      |  ← Before controller
|        |             |
|  [Controller runs]   |
|        |             |
|  2. postHandle()     |  ← After controller, before view
|        |             |
|  3. afterCompletion()|  ← After view rendered / response sent
+----------------------+
      |
      ▼
   Response


Interceptor Lifecycle — 3 Hook Methods

1. preHandle()
Runs before the controller method
Return true → allow request to proceed
Return false → block the request entirely

2. postHandle()
Runs after the controller method but before the view is rendered
Has access to ModelAndView — can modify data going to the view
Not called if preHandle() returned false
Not called if controller throws an exception

3. afterCompletion()
Runs after the view is rendered / response is committed
Always called as long as preHandle() returned true
Even called when an exception is thrown
Best place for cleanup (closing resources, logging duration)



@Component
public class MyInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) throws Exception {
        System.out.println("   URI: " + request.getRequestURI());
        // handler tells you which controller method will run
        if (handler instanceof HandlerMethod handlerMethod) {
            System.out.println("   Controller: " + handlerMethod.getBeanType().getSimpleName());
            System.out.println("   Method: " + handlerMethod.getMethod().getName());
        }

        return true; // true = proceed, false = block
    }

    @Override
    public void postHandle(HttpServletRequest request, HttpServletResponse response, Object handler, ModelAndView modelAndView) throws Exception {
        System.out.println("2. postHandle() called");
        if (modelAndView != null) {
            // can add data to the model here
            modelAndView.addObject("extraData", "added by interceptor");
        }
    }

    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response, Object handler, Exception ex) throws Exception {
        System.out.println("3. afterCompletion() called");
        if (ex != null) {
            System.out.println("   Exception occurred: " + ex.getMessage());
        }
    }
}

Unlike filters, interceptors must be manually registered in a config class:


@Configuration
public class WebConfig implements WebMvcConfigurer {

    @Autowired
    private MyInterceptor myInterceptor;

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(myInterceptor)
                .addPathPatterns("/api/**")       // apply to these URLs
                .excludePathPatterns("/api/login","/api/register"); // skip these URLs
    }
}

Types of Interceptors
1. Authentication / Role-based Interceptor
2. Logging / Execution Time Interceptor
3. Custom Annotation-based Interceptor
Reads a custom annotation on controller methods and acts on it.
4. Locale / Internationalization Interceptor
Changes language/locale based on request param or header.


Multiple Interceptors — Execution Order

registry.addInterceptor(loggingInterceptor).addPathPatterns("/**");  // order 1
registry.addInterceptor(authInterceptor).addPathPatterns("/**");     // order 2
registry.addInterceptor(roleInterceptor).addPathPatterns("/admin/**"); // order 3


Interceptor HandlerInfo : Knows exact controller class and method
Annotation reading : Can read custom annotations on controller methods
ModelAndView access : Can modify data going to the view in postHandle()

Filter and Interceptor both intercept requests
 but at different levels. Filter runs at Servlet
 level — before DispatcherServlet — so it sees
 ALL requests including static resources.
 Interceptor runs inside Spring MVC — after
 DispatcherServlet — so it knows which controller
 and method is handling the request.

 OncePerRequestFilter extends Filter and guarantees
 doFilterInternal runs exactly once per request,
 even if Spring internally forwards or dispatches
 the request multiple times.

 For logging, JWT validation, and CORS — I use
 OncePerRequestFilter. For role checks tied to
 specific controllers — Interceptor.
