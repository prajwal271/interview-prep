In Java, we use object references to connect things, NOT foreign key columns.

JPA (Java Persistence API) is a translator between Java objects and database tables.

class Author {
    Long id;
    String name;
    List<Book> books;       // ← Author HAS books (object reference)
}

class Book {
    Long id;
    String title;
    Author author;          // ← Book HAS an author (object reference)
}

Book book = new Book();
book.setAuthor(rowling);  // Java object reference
bookRepository.save(book);

INSERT INTO books (title, author_id) VALUES ('Harry Potter', 1);
                                                            ↑
                                       Java object → foreign key column

Book book = bookRepository.findById(1L).get();
String authorName = book.getAuthor().getName();  // Java object reference

SELECT * FROM books WHERE id = 1;
SELECT * FROM authors WHERE id = ?;   -- to get the author

This translation is called Object-Relational Mapping (ORM).

ORM is a technique that lets you work with database data using objects in your code, instead of writing SQL queries manually.

JPA gives us 4 annotations to express relationships in Java code:

@OneToOne	One Person has one Passport
@OneToMany	One Author has many Books
@ManyToOne	Many Books belong to one Author
@ManyToMany	Many Students enroll in many Courses



These annotations tell JPA: "Hey, this Java object reference should map to a foreign key in the database."

@ManyToOne means : many of this entity belong to ONE of that entity

Many Books belong to One Author
Many Employees belong to One Department

public class Book {
    @ManyToOne          // ← "Many Books to One Author"
    private Author author;
}

What @ManyToOne Gives You
It tells JPA: "This Java object reference IS a foreign key in the database."

@ManyToOne
@JoinColumn(name = "author_id")
private Author author;

CREATE TABLE books (
    id BIGINT PRIMARY KEY,
    title VARCHAR(255),
    author_id BIGINT,                                      -- ← FK column
    FOREIGN KEY (author_id) REFERENCES authors(id)         -- ← FK constraint
);


@Entity
@Table(name = "borrow_records")
public class BorrowRecord {
    
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    
    @ManyToOne(fetch = FetchType.LAZY)        // ← Many borrows → One user
    @JoinColumn(name = "user_id", nullable = false)
    private User user;
    
    @ManyToOne(fetch = FetchType.LAZY)        // ← Many borrows → One book
    @JoinColumn(name = "book_id", nullable = false)
    private Book book;
    
    @Column(nullable = false)
    private LocalDateTime borrowedAt = LocalDateTime.now();
    
    private LocalDateTime returnedAt;          // null = still borrowed
}

CREATE TABLE borrow_records (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id BIGINT NOT NULL,                          -- ← FK from @ManyToOne User
    book_id BIGINT NOT NULL,                          -- ← FK from @ManyToOne Book
    borrowed_at TIMESTAMP NOT NULL,
    returned_at TIMESTAMP,
    
    FOREIGN KEY (user_id) REFERENCES users(id),
    FOREIGN KEY (book_id) REFERENCES books(id)
);

@ManyToOne turns a foreign key column into a Java object reference. That's its whole job.

It maps a foreign key column in the database to a Java object reference. It goes on the entity that has the FK column — the 'many' side.
Where does the FK column live — in the parent table or the child table?
Always in the child (many) table. That's why @ManyToOne goes on the child.


@ManyToMany 
Many of this Entity relate to many of that entity

Many Students enroll to Many Courses
Many Movies contains Many Actors


For @ManyToOne, the FK lives in the "many" side. Easy.
But for @ManyToMany... where would the FK live?


A single column can only hold one value, but each side has many related entities.
Solution: A Join Table (a third table!)
We create a separate table just to store the relationships:

students table         student_course (join table)         courses table

The join table is the glue between the two main tables.

How JPA Handles It

@Entity
@Table(name = "students")
public class Student {
    @Id @GeneratedValue
    private Long id;
    private String name;
    
    @ManyToMany
    @JoinTable(
        name = "student_course",                            // ← join table name
        joinColumns = @JoinColumn(name = "student_id"),     // ← my FK in join table
        inverseJoinColumns = @JoinColumn(name = "course_id") // ← their FK in join table
    )
    private Set<Course> courses = new HashSet<>();
}


@Entity
@Table(name = "courses")
public class Course {
    @Id @GeneratedValue
    private Long id;
    private String title;
    
    @ManyToMany(mappedBy = "courses")        // ← inverse side (no @JoinTable)
    private Set<Student> students = new HashSet<>();
}

@ManyToMany Limitations & Best Practice
You can't store EXTRA data in the join table 
What if you want to track WHEN a student enrolled? Or their grade?
Solution: Convert to two @ManyToOne relationships with an entity

Instead of @ManyToMany, create an actual Enrollment entity:

@Entity
@Table(name = "enrollments")
public class Enrollment {
    @Id @GeneratedValue
    private Long id;
    
    @ManyToOne
    @JoinColumn(name = "student_id")
    private Student student;
    
    @ManyToOne
    @JoinColumn(name = "course_id")
    private Course course;
    
    private LocalDate enrolledAt;     // ← extra data!
    private String grade;             // ← extra data!
}

@OneToMany(mappedBy = "student")
private List<Enrollment> enrollments;

Best practice in production: Avoid @ManyToMany. Use a join entity with two @ManyToOne instead. It's more flexible.

@ManyToOne	In the MANY side's table	Many Books → One Author
@OneToMany	(No FK — uses mappedBy)		One Author → Many Books (inverse)
@ManyToMany	In a separate join table	Many Students ↔ Many Courses


"When would you use @ManyToMany?"
"When both sides have multiple connections to the other AND you don't need extra metadata about the relationship itself. Example: Posts and Tags."

"When should you AVOID @ManyToMany?"
"When you need to store extra data on the relationship (timestamp, status, role). Then use a join entity with two @ManyToOne."

"What's the difference between @JoinColumn and @JoinTable?"
"@JoinColumn defines a single FK column (used by @ManyToOne). @JoinTable defines a separate junction table (used by @ManyToMany)."

						The N+1 Problem

The N+1 problem is when you expect to fire 1 query but JPA secretly fires N+1 queries — one for the parent + N for each child.

It's a silent performance killer. Your code looks fine, returns correct results, but underneath, it's hammering the database with hundreds or thousands of unnecessary queries.

Scenario: Show all active borrow records with user name and book title

List<BorrowRecord> activeBorrows = borrowRepository.findByReturnedAtIsNull();

for (BorrowRecord record : activeBorrows) {
    System.out.println(
        record.getUser().getName() + " borrowed " + record.getBook().getTitle()
    );
}

Suppose there are 3 active borrow records in the database.

What ACTUALLY Happens (with LAZY fetch)

@ManyToOne(fetch = FetchType.LAZY)
private User user;

@ManyToOne(fetch = FetchType.LAZY)
private Book book;

LAZY = "Don't load related entities until I actually call .getUser() or .getBook()."

Internally SQL queries 

-- Step 1: findByReturnedAtIsNull()
SELECT id, user_id, book_id, borrowed_at, returned_at
FROM borrow_records
WHERE returned_at IS NULL;
-- Returns 3 records

-- Now we enter the for loop...

-- Iteration 1: record.getUser() triggers query!
SELECT id, name FROM users WHERE id = 1;
-- Iteration 1: record.getBook() triggers another query!
SELECT id, title FROM books WHERE id = 5;

-- Iteration 2: record.getUser()
SELECT id, name FROM users WHERE id = 2;
-- Iteration 2: record.getBook()
SELECT id, title FROM books WHERE id = 7;

-- Iteration 3: record.getUser()
SELECT id, name FROM users WHERE id = 3;
-- Iteration 3: record.getBook()
SELECT id, title FROM books WHERE id = 9;

Total queries fired: 1 (for borrows) + 3 (users) + 3 (books) = 7 queries 

Scaling It Up — The Real Horror

10K Borrows = 1 + 10k + 10k = 20k+1 queries
This is what makes a "fast in dev, slow in production" bug.

Here in code we have used lazy loading 
The difference: with LAZY, the extra queries fire when you call .getUser(). With EAGER, they fire immediately after the parent query. Same total count: N+1 queries.

You can't fix what you can't see. Always enable SQL logging during development

spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true
logging.level.org.hibernate.SQL=DEBUG
logging.level.org.hibernate.type.descriptor.sql.BasicBinder=TRACE

Now every query is printed to the console. Run the loop, count the queries:

The goal: Reduce N+1 queries down to 1 query by using SQL JOIN.
-- The 1-query version we WANT:
SELECT br.*, u.*, b.*
FROM   borrow_records br
JOIN   users u ON br.user_id = u.id
JOIN   books b ON br.book_id = b.id
WHERE  br.returned_at IS NULL;

FIX 1: @EntityGraph (BEST — most targeted)
Add @EntityGraph to the repository method to specify what to fetch eagerly just for that query:

@Repository
public interface BorrowRepository extends JpaRepository<BorrowRecord, Long> {
    
    @EntityGraph(attributePaths = {"user", "book"})    // ← magic!
    List<BorrowRecord> findByReturnedAtIsNull();
}

attributePaths = {"user", "book"} tells JPA:
When you run this query, JOIN-FETCH the user and book relationships in one go.

SELECT br.id, br.borrowed_at, br.returned_at, br.user_id, br.book_id,
       u.id, u.name,
       b.id, b.title, b.available
FROM   borrow_records br
LEFT JOIN users u ON br.user_id = u.id
LEFT JOIN books b ON br.book_id = b.id
WHERE  br.returned_at IS NULL;

Why is this the BEST option?
Only this query joins user + book. Other queries stay LAZY
You don't write JPQL — clean and short
Easy to define multiple entity graphs for different scenarios

FIX 2: JOIN FETCH in @Query
Write the JPQL manually with JOIN FETCH

@Repository
public interface BorrowRepository extends JpaRepository<BorrowRecord, Long> {
    
    @Query("SELECT br FROM BorrowRecord br " +
           "JOIN FETCH br.user " +              // ← join + load user
           "JOIN FETCH br.book " +              // ← join + load book
           "WHERE br.returnedAt IS NULL")
    List<BorrowRecord> findActiveBorrows();
}

@EntityGraph and @JoinFetch both are same but 
Entity graph joins tables and does not load them into the memory but Join fetch loads them into the memory

"Difference between JOIN and JOIN FETCH?"
"JOIN joins tables in SQL but doesn't load related entities into memory — they remain proxies. JOIN FETCH joins AND loads them. To fix N+1, you need JOIN FETCH."

What is CascadeType?
CascadeType tells JPA: "When I do an operation on the parent (save, delete, etc.), automatically apply the SAME operation to the children.
If I delete an Author, also delete all her Books. Don't make me do it manually


User john = userRepository.findById(1L).get();

// Step 1: manually delete all borrow records first
List<BorrowRecord> records = borrowRepository.findByUser(john);
for (BorrowRecord record : records) {
    borrowRepository.delete(record);
}

// Step 2: now safely delete the user
userRepository.delete(john);


With Cascade

@OneToMany(mappedBy = "user", cascade = CascadeType.ALL)
private List<BorrowRecord> borrowRecords;

userRepository.delete(john);    // ← cascades to borrowRecords automatically!
JPA handles the deletion of related records for you. 


The CascadeType Options
JPA gives you 6 cascade types + a convenient ALL

PERSIST		save() (new entities)		Saving parent saves new children
MERGE		save() (existing)		Updating parent updates children
REMOVE		delete()			Deleting parent deletes children
REFRESH		refresh()			Reloading parent reloads children
DETACH		detach()			Detaching parent detaches children
ALL		Everything above		All operations cascade



@OneToMany(mappedBy = "user", cascade = CascadeType.REMOVE)
private List<BorrowRecord> borrowRecords;

userRepository.deleteById(5L);

-- Step 1: Delete child records FIRST (foreign key dependency!)
DELETE FROM borrow_records WHERE user_id = 5;

-- Step 2: Then delete the parent
DELETE FROM users WHERE id = 5;

Children are deleted first, parent second. Otherwise the FK constraint would fail!

Hard deletes are forever. Soft deletes are reversible. Choose wisely. 

@OneToMany(cascade = CascadeType.REMOVE)
JPA emits separate DELETE statements:
DELETE FROM borrow_records WHERE user_id = 5;
DELETE FROM users WHERE id = 5;
