JPA = the spec. Hibernate = the actual product that follows the spec.

You could swap Apple's charger for Anker's — both follow USB-C. Same deal: you could swap Hibernate for EclipseLink or OpenJPA — same JPA code, different engine.

Spring Data JPA = a Spring abstraction over JPA. It gives you the magic JpaRepository<Book, Long> interface so you don't have to write boilerplate code. But under the hood, it's still using JPA → Hibernate → DB.

JPA is a specification — it defines annotations and interfaces like @Entity and EntityManager but has no actual implementation. Hibernate is the most popular implementation of JPA — it generates the SQL, handles caching, and talks to the database. Spring Data JPA sits on top, giving us repository abstractions like JpaRepository. So when I write @Entity and bookRepository.save(book), JPA defines the rules, Spring Data JPA simplifies the code, and Hibernate does the actual SQL execution.

@Entity
@Table(name = "books")
public class Book {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    
    private String title;
}

@Entity — "I'm a Table"
Class must have a no-arg constructor (public or protected) 
	JPA needs to instantiate your entity when reading from the database — before it has the data to populate the fields. The standard sequence is:
	// What Hibernate does internally:
	User user = User.class.getDeclaredConstructor().newInstance();  // 1. create empty instance
	user.setId(...);     // 2. populate via reflection
	user.setName(...);
	user.setEmail(...);

Can you have an all-args constructor?
Yes — you absolutely can. This is a common misconception. The rule is:

✅ You can also have an all-args constructor (or any other constructor)
Must have at least one @Id field
Class cannot be final

@NoArgsConstructor(access = AccessLevel.PROTECTED)  // for JPA

Not final Hibernate generates runtime subclass proxies for lazy loading and dirty checking

@Table — Customize the Table

Adding indexes via @Table(indexes=...) creates them as part of the schema generated by Hibernate. But in production, prefer Flyway migrations for indexes — gives you version control over schema changes.

3️⃣ @Id + @GeneratedValue — The Primary Key

@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;

IDENTITY DB auto-increment (Postgres BIGSERIAL, MySQL AUTO_INCREMENT)
SEQUENCE DB sequence object (Postgres/Oracle native sequences)
TABLE Hibernate maintains a separate table of "next ID" values
AUTO Hibernate picks for you

IDENTITY is simpler — DB auto-generates the ID. But it disables JDBC batch inserts because Hibernate must fetch the generated ID after each insert. SEQUENCE allows pre-fetching IDs in batches (allocationSize=50), so you can insert 50 rows in one batch. For high-throughput inserts, prefer SEQUENCE

8️⃣ Lifecycle Callbacks — Hook into Save/Load Events
JPA lets you run code at specific points in an entity's lifecycle:

@Entity
public class Book {
    @Id private Long id;
    private LocalDateTime createdAt;
    private LocalDateTime updatedAt;
    
    @PrePersist          // Runs BEFORE the first INSERT
    void beforeSave() {
        createdAt = LocalDateTime.now();
        updatedAt = LocalDateTime.now();
    }
    
    @PreUpdate           // Runs BEFORE every UPDATE
    void beforeUpdate() {
        updatedAt = LocalDateTime.now();
    }
    
    @PostLoad            // Runs AFTER reading from DB
    void afterLoad() {
        // E.g., decrypt sensitive fields
    }
}

Q1: "Why does JPA require a no-arg constructor?"
"Hibernate creates entity instances using reflection — it calls Class.newInstance(), which requires a no-arg constructor. Then it sets field values from DB results. Without it, Hibernate throws InstantiationException at runtime."

Q2: "What's the difference between @Column(nullable=false) and @NotNull?"
"@Column(nullable=false) is a JPA annotation — it adds a NOT NULL constraint to the DB schema. @NotNull is a Bean Validation annotation — it validates at the Java level before save. Use both: schema-level prevents bad data even if the app fails; Java-level catches errors before hitting the DB."

Q3: "Why use EnumType.STRING over ORDINAL?"
"ORDINAL stores the enum's position (0, 1, 2). If anyone reorders the enum or inserts a new value at the start, all existing DB data points to the wrong enum. STRING stores the name — refactor-safe."

Q4: "When would you use @Transient?"
"For fields computed at runtime that shouldn't persist — derived values like 'yearsOld', cached external API results, or UI helper flags."

Q5: "What's @Column(updatable=false) good for?"
"Audit fields like createdAt — set once on insert, never updated again. Prevents accidental overwrites in subsequent saves."


Topic 3: JpaRepository & Derived Queries

The Problem It Solves 
Without Spring Data JPA, every CRUD operation requires writing this kind of code:


public class BookDao {
    @PersistenceContext
    private EntityManager em;
    
    public Book findById(Long id) {
        return em.find(Book.class, id);
    }
    
    public List<Book> findAll() {
        return em.createQuery("SELECT b FROM Book b", Book.class).getResultList();
    }
    
    public List<Book> findByAuthor(String author) {
        return em.createQuery("SELECT b FROM Book b WHERE b.author = :author", Book.class)
                 .setParameter("author", author)
                 .getResultList();
    }
    
    public Book save(Book book) {
        em.persist(book);
        return book;
    }
    
    public void delete(Long id) {
        em.remove(em.find(Book.class, id));
    }
    
    // ... 30 more methods for each operation
}

Boilerplate hell. Every entity needs the same boring methods. 


Spring Data JPA replaces ALL of that with one interface:

public interface BookRepository extends JpaRepository<Book, Long> {
}

Spring auto-generates:

bookRepository.save(book);
bookRepository.findById(1L);
bookRepository.findAll();
bookRepository.deleteById(1L);
bookRepository.count();
bookRepository.existsById(1L);
// ... 17+ more methods, all free


You don't write the implementation. Spring creates a proxy class at startup and injects it.

              PagingAndSortingRepository<T, ID>

 You can add this method to your repository:

public interface BookRepository extends JpaRepository<Book, Long> {

SELECT * FROM books WHERE author = ?

You wrote ZERO SQL. ZERO implementation.

🛠️ When Derived Queries Aren't Enough: @Query
Sometimes the method name gets too ugly:

List<Book> findByAuthorAndStatusAndPublishedDateAfterAndTitleContainingIgnoreCase(...);
//                          ↑ this method name is 90 characters of pain 😩

When this happens, write the JPQL yourself with @Query:

public interface BookRepository extends JpaRepository<Book, Long> {
    
    @Query("SELECT b FROM Book b " +
           "WHERE b.author = :author " +
           "AND b.status = :status " +
           "AND b.publishedDate > :date " +
           "AND LOWER(b.title) LIKE LOWER(CONCAT('%', :keyword, '%'))")
    List<Book> searchBooks(
            @Param("author") String author,
            @Param("status") BookStatus status,
            @Param("date") LocalDate date,
            @Param("keyword") String keyword);
}


Two flavors of @Query:

// JPQL (default) — works with entities
@Query("SELECT b FROM Book b WHERE b.author = :author")

// Native SQL — write raw DB-specific SQL
@Query(value = "SELECT * FROM books WHERE author = :author", nativeQuery = true)


✏️ Modifying Queries (UPDATE / DELETE)
Use @Modifying for updates:

@Modifying
@Transactional
@Query("UPDATE Book b SET b.status = :status WHERE b.author = :author")
int markAllBooksByAuthorAs(@Param("author") String author, @Param("status") BookStatus status);


Q1: "How does Spring Data know the SQL to generate from a method name?"
"At startup, Spring scans every interface that extends JpaRepository, parses each method name using a special name-parser, and creates a proxy implementation. The parser splits names like 'findByAuthorAndStatus' into a query template, then binds method parameters to the WHERE clauses."

Q2: "What's the difference between JpaRepository and CrudRepository?"
"CrudRepository gives you basic CRUD methods. JpaRepository extends it with paging, sorting, batch operations (saveAll, deleteAllInBatch), and JPA-specific features like flush(). Most projects use JpaRepository for the extra features."

Q3: "When would you use @Query over derived queries?"
"When the method name would become unreadably long (5+ conditions), when you need JOINs, when you need DB-specific SQL features, or when you need optimization with @EntityGraph. Derived queries are great for simple cases — @Query for everything else."

Q4: "What's the difference between @Query JPQL and native SQL?"
"JPQL works with entity names and field names — it's database-portable. Native SQL uses actual table/column names — DB-specific but allows features JPQL doesn't support (window functions, CTEs, vendor extensions like PostgreSQL's JSON operators)."

Q5: "Why do @Modifying queries need @Transactional?"
"Modifying queries (UPDATE/DELETE) write to the database, which requires an active transaction. Without @Transactional, Spring throws TransactionRequiredException. Service methods calling these should also be @Transactional."

Where to use @Transactional
Use it on service layer methods that modify the database.

@Service
public class UserService {
    
    @Transactional  // ✅ here
    public void transferMoney(Long from, Long to, BigDecimal amount) {
        accountRepo.debit(from, amount);
        accountRepo.credit(to, amount);
    }
}

Why service layer (not controller, not repository)

Controller → too high, mixes web with DB logic
Repository → too low, each call is its own transaction; you can't group multiple DB calls
Service → just right, one business operation = one transaction

Common mistake 

@Service
public class UserService {
    
    public void outer() {
        inner();  // ❌ @Transactional ignored — same-class call
    }
    
    @Transactional
    public void inner() { ... }
}

1️⃣ Unidirectional @ManyToOne (Simplest, Most Common)
If you only ever need to navigate from BorrowRecord to User, do this:

@Entity
public class BorrowRecord {
    @Id @GeneratedValue
    private Long id;
    
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "user_id")
    private User user;
}

@Entity
public class User {
    @Id @GeneratedValue
    private Long id;
    private String name;
    
    // No @OneToMany — User doesn't know about its borrows
}

BorrowRecord br = borrowRepo.findById(1L).get();
User u = br.getUser();  // ✅ Works
String name = u.getName();

2️⃣ Bidirectional Relationship — Both Sides Know
Sometimes you want to do user.getBorrowRecords() directly. Then you need bidirectional:

@Entity
public class User {
    @Id @GeneratedValue
    private Long id;
    private String name;
    
    @OneToMany(
        mappedBy = "user",                    // ⭐ Critical!
        fetch = FetchType.LAZY,
        cascade = CascadeType.ALL,
        orphanRemoval = true
    )
    private List<BorrowRecord> borrowRecords = new ArrayList<>();
}

@Entity
public class BorrowRecord {
    @Id @GeneratedValue
    private Long id;
    
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "user_id")
    private User user;
}

user.getBorrowRecords();    // ✅ Works
borrowRecord.getUser();     // ✅ Works

But this opens a Pandora's box of gotchas. Let's break each one. 

1) mappedBy — The Most Important Word

@OneToMany(mappedBy = "user")  // ← what is this?
private List<BorrowRecord> borrowRecords;

mappedBy = "user" means: "I'm NOT the owner of this relationship. The FK lives on the other side, in the field named 'user'."

Without mappedBy, JPA gets confused and creates a 3rd table (a join table):

-- WITHOUT mappedBy (BAD!)
CREATE TABLE user_borrow_records (
    user_id BIGINT,
    borrow_record_id BIGINT
);
-- Plus borrow_records still has its own user_id column
-- → DUPLICATED data, broken design 💀

Rule: ALWAYS use mappedBy on @OneToMany. Always. Always

Memory trick: 
"@ManyToOne owns the FK. @OneToMany is mapped BY the @ManyToOne side."



2) Cascade — What Happens to Children When Parent Dies?

@OneToMany(mappedBy = "user", cascade = CascadeType.ALL)
private List<BorrowRecord> borrowRecords;

Cascade controls what happens to BorrowRecords when User is saved/deleted/etc.

3) orphanRemoval — Cascade's Cousin

@OneToMany(mappedBy = "user", orphanRemoval = true)
private List<BorrowRecord> borrowRecords;

orphanRemoval = true means: "If a child is removed from this collection, DELETE it from the DB.

4)The Sync Trap (Most Common Bug!)
When you have a bidirectional relationship, both sides must be updated manually:
User user = new User("Alice");
BorrowRecord br = new BorrowRecord();

br.setUser(user);                       // Set ONE side
user.getBorrowRecords().add(br);        // Set OTHER side too!

userRepo.save(user);

5) The Infinite Recursion in JSON Serialization
You build a REST API. You return a User. Spring tries to convert it to JSON:

@GetMapping("/users/1")
public User getUser() {
    return userRepo.findById(1L).get();
}

User → has borrowRecords → each borrow has user → which has borrowRecords → 💥
Result: StackOverflowError from infinite JSON recursion. 

3 ways to fix:
Fix 1: @JsonIgnore on one side
@OneToMany(mappedBy = "user")
@JsonIgnore                      // Don't serialize this side
private List<BorrowRecord> borrowRecords;

6) N+1 Strikes Again (with @OneToMany!)
Fix with @EntityGraph

Putting It All Together: Production-Quality Bidirectional
@Entity
@Table(name = "users")
public class User {
    
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    
    private String name;
    
    @OneToMany(
        mappedBy = "user",
        cascade = {CascadeType.PERSIST, CascadeType.MERGE},  // NO REMOVE — preserve history
        orphanRemoval = false,
        fetch = FetchType.LAZY                                // ALWAYS LAZY
    )
    @JsonIgnore                                                // Avoid recursion
    private List<BorrowRecord> borrowRecords = new ArrayList<>();
    
    // Helper methods to keep both sides in sync
    public void addBorrow(BorrowRecord br) {
        borrowRecords.add(br);
        br.setUser(this);
    }
    
    public void removeBorrow(BorrowRecord br) {
        borrowRecords.remove(br);
        br.setUser(null);
    }
}

@Entity
@Table(name = "borrow_records")
public class BorrowRecord {
    
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "user_id", nullable = false)
    private User user;
    
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "book_id", nullable = false)
    private Book book;
    
    private LocalDateTime borrowedAt;
    private LocalDateTime returnedAt;
}



Q1: "What does mappedBy do, and what happens without it?"
"mappedBy tells JPA that THIS side is the inverse — the FK lives in the other entity, named in the mappedBy value. Without it on @OneToMany, JPA assumes both sides are owners and creates a separate join table, duplicating data and breaking the model."

Q2: "Should you use unidirectional or bidirectional relationships?"
"Unidirectional by default — simpler, less to maintain, fewer bugs. Use bidirectional only when you genuinely need to navigate from both sides AND you want to use cascade/orphanRemoval from the parent. Most modern codebases prefer querying via repository methods over bidirectional navigation."

Q3: "What's the difference between cascade.REMOVE and orphanRemoval?"
"Cascade.REMOVE deletes children when parent is deleted. orphanRemoval deletes children when they're removed from the collection (parent still alive). They're independent — you can use either, both, or neither depending on the semantics."

Q4: "Why fetch = LAZY for @OneToMany?"
"EAGER on @OneToMany loads the entire children collection every time the parent is loaded. For a User with 1000 borrow records, that's 1000 rows pulled even when you just want the user's name. LAZY defers loading until actually needed; combine with @EntityGraph for queries that DO need the children."

Q5: "How do you avoid infinite recursion when serializing entities to JSON?"
"Best practice: don't serialize entities directly — use DTOs. If you must, use @JsonIgnore on one side, or @JsonManagedReference/@JsonBackReference to clearly mark which side serializes. DTOs also prevent over-fetching and decouple API from DB schema."

JOIN vs JOIN FETCH

Customer table
id	name
1	Ravi
2	Priya
3	Amit

Order table
id	customer_id
101	1
102	1
103	2

So: Ravi has 2 orders, Priya has 1, Amit has none.

JOIN — "peek but don't bring"

Think of JOIN like peeking into the customer table just to filter, but you walk away with only orders in your hand.

SELECT o FROM Order o JOIN o.customer c WHERE c.name = 'Ravi'

What you get back: 101,102

Going to a shop, asking "show me items bought by Ravi" — they show you items, but Ravi himself isn't with you. If you want Ravi's details, you have to ask again.

JOIN FETCH — "peek AND bring along"
JOIN FETCH means peek into customer table AND carry the customer along with the order.

SELECT o FROM Order o JOIN FETCH o.customer WHERE o.id = 101

What you get back: 101 Ravi

Plain JOIN — used for FILTERING in WHERE
JOIN FETCH — used for LOADING the related entity

JOIN filters, JOIN FETCH loads

@Query("SELECT u FROM User u JOIN FETCH u.borrowRecords")

Simple queries (just need to fetch relationships) → @EntityGraph
Complex queries (custom WHERE, JOINs for filtering) → @Query with JOIN FETCH

"How do you fix N+1?", here's your gold-standard response:

"There are 3 main approaches, each with trade-offs:
1. JOIN FETCH in JPQL — Most explicit, generates a single SQL with JOINs. Be careful with pagination on collections — Hibernate falls back to in-memory pagination.
2. @EntityGraph — Cleaner declarative syntax. I prefer this for repository methods because it can be combined with derived queries.
3. Batch fetching with @BatchSize or default_batch_fetch_size — When you can't predict at compile time whether you need the relationship. Hibernate batches lazy loads into IN queries.
For pure read APIs, I prefer DTO projection with SELECT new DTO(...) — it skips entity loading entirely and returns only the columns needed.
I detect N+1 in dev by enabling spring.jpa.show-sql=true and watching for repeated similar queries during a single request."


what happens when one @Transactional method calls ANOTHER @Transactional method?
This is where propagation comes in.

@Service
public class BorrowingService {
    
    @Transactional                 // Outer transaction
    public void borrowBook(...) {
        bookRepo.save(book);
        auditService.logAction(...);  // What happens here?
    }
}

@Service
public class AuditService {
    
    @Transactional                 // Inner transaction — what does this mean?
    public void logAction(...) {
        auditRepo.save(...);
    }
}

The question: Does logAction join the existing transaction, or start its own?
The answer depends on the propagation type

JPA defines 7 propagation behaviors. You'll mostly use two: REQUIRED and REQUIRES_NEW

REQUIRED (default) :  Join existing tx, or create new if none
REQUIRES_NEW       :  ALWAYS create a new tx, suspend the existing one

1️⃣ REQUIRED (The Default)
If a transaction already exists, JOIN it. Otherwise, START a new one

What happens the same method above 

Caller starts transaction T1
   ↓
   bookRepo.save(book)              ← inside T1
   ↓
   auditService.logAction()
      ↓
      auditRepo.save(...)           ← STILL inside T1 (joined)
   ↓
   Method returns successfully
COMMIT T1                            ← One commit for everything



@Transactional(propagation = Propagation.REQUIRED)   // Outer
public void borrowBook() {
    bookRepo.save(book);
    
    try {
        riskyService.doSomething();    // Inner method also REQUIRED — joins T1
    } catch (Exception e) {
        // ⚠️ I caught the exception, so I keep going!
        log.warn("Risky failed, oh well");
    }
    
    // I expect this to commit...
}


riskyService.doSomething() throws → marks T1 for rollback
You catch the exception → method continues normally
At commit time → Spring sees T1 is marked rollback-only → UnexpectedRollbackException 

Why? Because both methods were in the SAME transaction. When the inner one failed, it poisoned the whole transaction.

Use REQUIRES_NEW for the risky inner method (we'll see this next)

2️⃣ REQUIRES_NEW (The "Independent Transaction")
Behavior: "ALWAYS start a brand new transaction. SUSPEND the existing one if any."

@Transactional(propagation = Propagation.REQUIRES_NEW)
public void logAuditEvent(String action) {

Two independent commits. They cannot affect each other

REQUIRED is the default — it joins an existing transaction if one exists, or creates a new one if not. REQUIRES_NEW always creates a brand-new transaction and suspends any existing one. The key difference is independence: with REQUIRED, an inner failure rolls back the outer; with REQUIRES_NEW, the inner commits or rolls back independently.
Classic use case: audit logging with REQUIRES_NEW so audit records persist even when the main business transaction fails. Important caveat: REQUIRES_NEW uses 2 DB connections simultaneously, so I avoid overusing it to prevent connection pool exhaustion. Also — @Transactional only works through Spring's proxy, so self-invocation within the same class bypasses it entirely. The annotated method must be on a different bean
